# 系统化调试（systematic-debugging）

## ⚖️ IRON LAW（不可协商）

**未定位到可复现的根因（root cause），不得编写任何修复代码。**

## 🚩 红旗清单（识别即停，回到 IRON LAW）

- "先试试改这里，可能就好了" → 停，你在猜，不是在调试
- "加个 try/catch 把异常吞掉" → 停，这是掩盖不是修复
- "重启/重跑一下应该就正常了" → 停，间歇性问题更需要根因
- "看起来是 X 导致的" → "看起来"是红旗，去证明它
- 以及共享红旗词表（见 `../_shared/iron-law.md`）

## 四阶段方法论

### 阶段 1 — 复现（Reproduce）
- 找到**稳定复现**的最小路径。无法复现就先解决复现问题，不许凭空修
- 记录：触发条件、预期行为、实际行为、环境

### 阶段 2 — 定位根因（Root Cause）
- 用二分/日志/断点逐层缩小，直到指向**确切的那一行/那个状态**
- 区分"症状出现的地方"和"问题产生的地方"——它们常常不在一处
- 写下根因假设，并用一个实验**证伪或证实**它，不停在"我觉得"

### 阶段 3 — 最小验证（Verify the Cause）
- 在动手修复前，先用最小改动（甚至只是一行打印）**证明**"改变这个根因确实改变了症状"
- 证明不了，说明根因判断错了，回阶段 2

### 阶段 4 — 修复并加回归测试（Fix + Regression）
- 写一个**会因这个 bug 而失败**的测试（先红，复用 tdd skill）
- 再写修复让它变绿
- 这条回归测试永久留下，防止复发
- emit `debug.rootcause.found` / `debug.fix.verified`

## 输出

调试结论写入当前任务的 `.sop/changelog.md`（作为一条 type=fix 的 CR），"解决什么问题"一节必须写清根因，而非现象。
